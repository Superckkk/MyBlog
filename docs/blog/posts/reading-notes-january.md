# 一月的几本书和几件小事

占位文章，演示一下标签、分类、阅读时长这些元素凑在一起的样子。
内容是真的在读的东西，但写得很随意。

<!-- more -->

## 《Designing Data-Intensive Applications》重读

第二遍读，感受完全不一样。第一遍读的时候满脑子都是"这个概念好酷"，
第二遍读才发现作者其实一直在讲同一件事：**分布式系统里没有免费的午餐，
每一个看似简单的保证背后都有一个具体的代价**。

比如一致性模型那一章，第一次读的时候记了一堆名词：
线性一致、顺序一致、因果一致……第二次读才注意到作者反复在问同一个问题：

> 这个保证，在什么故障模型下成立？

如果网络分区不发生，什么模型都成立。所以真正要问的是——分区发生了会怎样。

顺手记一下这几种模型的强弱关系：

```text
线性一致  >  顺序一致  >  因果一致  >  最终一致
（最强）                                （最弱）
```

## 《The Staff Engineer's Path》

前半本讲"三种工作模式"的部分挺实用：技术负责人、架构师、问题解决者，
作者说这三者需要的能力其实不一样，很多人卡住是因为一直用其中一种模式
应对所有场景。

后半本讲沟通的部分有点像管理类书籍的通病——道理都对，
但具体到"明天的评审会我该怎么说"就帮不上忙了。

## 一件小事：把 dotfiles 整理了一遍

起因是换了台机器，发现自己的 `.gitconfig` 里有七个别名是从别人那儿抄的，
自己从来没用过，还有两个互相覆盖。

清理之后剩下来的这些是真在用的：

```ini
[alias]
    st = status -sb
    lg = log --oneline --graph --decorate -20
    amend = commit --amend --no-edit
    unstage = restore --staged
```

具体的写在[笔记里](../../notes/tooling/git-aliases.md)了。

## 一个想法

> 写文档的时候，假设读者是三个月后的自己——他会记得今天讨论的上下文吗？

这条是从某次事故复盘里抄来的。当时有个配置项的默认值改过，
改的人、审的人、部署的人都以为对方知道，结果线上跑了两个月没人发现。

现在写配置注释都会多写一句"为什么是这个值"，哪怕看起来很蠢。
